개요

Overview

과학기술정보통신부(과기부)는 스타트업에게 중요한 사업공고를 지속적으로 게시하지만, 다른 정부 사이트와 달리 공개 API를 제공하지 않습니다.

중소벤처기업부, 특허청 등 기존에 연동해 온 사이트들은 API 키 발급을 통해 데이터를 자동으로 수집할 수 있습니다. 반면 과기부는 별도의 데이터 접근 창구가 없어, 신규 공고 여부를 담당자가 직접 사이트에 접속해 수작업으로 확인해야 했습니다.

이 프로젝트는 그 공백을 해결하기 위해 구축되었습니다. 시스템이 6시간 주기로 과기부 사이트를 자동 점검하고, 공고 내용을 분석해 구조화된 정보로 정리한 뒤, 포트폴리오사와의 관련성을 판단합니다.

이전 (Before)

담당자가 과기부 사이트에 직접 접속해, 새 공고가 올라왔는지 눈으로 확인. 공고문을 열어 예산·자격·마감일을 일일이 읽고 정리.

이후 (After)

시스템이 6시간마다 자동으로 확인하고, 필요한 정보를 구조화해 정리. 담당자는 검색·필터로 필요한 공고만 바로 확인.

GitHub

Vercel

실제 웹사이트를 배포하고, GitHub에 코드가 반영될 때마다 자동으로 최신 버전을 업데이트합니다.

전체적 파이프라인 구조

Full pipeline architecture
STEP 1

수집 (Scrape)

과기부 사업공고 게시판을 확인해, 새로 올라온 공고를 찾아 원문과 첨부파일을 가져옵니다.

STEP 2

추출 (Extract)

첨부된 .hwpx 공고문을 열어 전체 텍스트를 읽고, AI가 예산·자격·마감일 등을 구조화된 데이터로 정리합니다.

구축 완료 · 대기중

색인 (Embed)

공고 내용을 의미 벡터로 변환해, 키워드가 아닌 “의미”로 검색할 수 있게 하는 기능입니다. 시맨틱 검색 활성화 이후 본격 가동 예정입니다.

구축 완료 · 대기중

매칭 (Match)

각 공고를 포트폴리오사와 비교해 AI가 관련성 점수를 매기는 기능입니다. 포트폴리오사 목록 입력 후 가동 예정입니다.

5

정확도 검증

Accuracy validation

542건을 전부 손으로 확인할 수는 없기 때문에, 무작위 표본 감사 방식으로 정확도를 검증했습니다.

공고를 무작위로 골라 실제 과기부 원문·첨부파일과 하나하나 대조하는 방식입니다. 통계적으로는 단순 무작위 표본(simple random sampling)을 이용한 정확도 감사에 해당합니다.

이 과정에서 실제로 두 가지 추출 오류를 발견하고 고쳤습니다 (다음 섹션 참고). 또한 우리 사이트의 공고 정렬 순서가 실제 과기부 사이트와 완전히 동일한 순서로 나오는지도 확인했습니다 — 같은 날 올라온 공고끼리도 과기부가 매기는 게시글 번호(ntt_seq_no) 순서를 그대로 따르도록 맞췄습니다.

Why this matters

표본 감사에서 발견한 오류는 실제로 코드에 반영해 542건 전체에 다시 적용했습니다 — 즉, 이 검증은 한 번의 점검이 아니라 실제로 데이터 품질을 끌어올린 과정이었습니다.

발견한 문제와 해결

Real bugs, found and fixed
FIXED

신청기간 표의 마감일이 뒤섞여 “미확인”으로 표시됨

많은 공고문이 신청기간을 표(表) 형식으로 제공합니다. 초기 버전은 문서를 문단 단위로만 읽었기 때문에, 표의 항목명(예: “접수마감일”)과 실제 날짜가 서로 분리된 채 저장되었습니다. 그 결과 실제로는 마감일이 명시되어 있는 공고인데도 사이트에는 “미확인”으로 표시되는 경우가 상당수 있었습니다.

→ 표의 행·열 구조를 그대로 인식해 항목명과 값을 정확히 짝지어 읽도록 파서를 재작성했습니다. 무작위 표본 재검사에서 정확도가 눈에 띄게 개선된 것을 확인했습니다.

FIXED

압축파일 속 공고문을 놓쳐 핵심 정보 누락

일부 공고는 실제 공고문(.hwpx)이 첨부파일로 바로 노출되지 않고, 압축파일(.zip) 안에 들어있었습니다. 기존 시스템은 압축파일 내부를 열어보지 않았기 때문에, 예산·자격요건 같은 핵심 정보를 아예 가져오지 못하고 있었습니다.

→ 압축파일을 자동으로 열어 내부의 공고문을 찾아 추출하도록 개선했습니다.

FIXED

같은 날 등록된 공고 순서가 과기부와 다르게 표시됨

과기부 사이트는 같은 날 등록된 공고끼리도 게시글 번호 순서를 정확히 지켜 보여줍니다. 초기 버전은 날짜만 기준으로 정렬했기 때문에, 같은 날짜 안에서는 순서가 뒤섞여 실제 사이트와 다르게 보이는 문제가 있었습니다.

→ 날짜가 같을 경우 과기부의 게시글 번호(ntt_seq_no)를 기준으로 2차 정렬하도록 수정해, 실제 사이트와 완전히 동일한 순서로 맞췄습니다.

FIXED

전체 공고 중 일부만 조회되던 문제

사용하는 데이터베이스(Supabase)는 한 번의 요청으로 최대 1,000건까지만 반환합니다. 이 한계를 인지하지 못해, 실제로는 542건이 있는데도 화면에는 그 일부만 표시되는 경우가 있었습니다.

→ 페이지 단위로 나눠 요청하도록 로직을 수정해, 전체 데이터가 빠짐없이 조회되도록 했습니다.

FIXED

보안 점검에서 발견된 접근 권한 문제

독립적인 보안 점검을 별도로 진행한 결과, 로그인 없이도 누구나 포트폴리오사 목록을 추가·수정·삭제할 수 있고, AI를 호출하는 핵심 기능도 제한 없이 실행할 수 있다는 점이 발견되었습니다. 방치할 경우 데이터 훼손이나 예상치 못한 비용 발생으로 이어질 수 있는 사안이었습니다.

→ 포트폴리오사 수정 권한과 핵심 자동화 기능에 별도의 관리자 인증을 도입해 접근을 제한했습니다.

How it's extracted

공고 원문과 첨부파일(.hwpx) 전체 텍스트를 AI(Gemini)에게 전달하고, 위 10개 항목에 맞춰 구조화된 형식으로 답하도록 요청하는 방식으로 이뤄집니다. 문서에 명시되지 않은 항목은 추측하지 않고 공란으로 남겨, 실제 공고 내용과 다른 값이 만들어지지 않도록 설계했습니다.

인덱싱과 시맨틱 검색

Currently in progress

Supabase·GitHub·Vercel 연동을 마친 지금, 다음 단계로 색인(indexing) 작업을 진행하고 있습니다.

인덱싱이란

책 뒤의 “찾아보기”와 같은 개념입니다. 색인이 없으면 원하는 내용을 찾기 위해 책 전체를 처음부터 읽어야 하지만, 색인이 있으면 바로 해당 페이지로 넘어갈 수 있습니다. 데이터베이스에서도 똑같이, 미리 정리된 색인 구조 덕분에 542건 전체를 하나씩 훑지 않고 원하는 결과로 바로 찾아갑니다.

시맨틱 검색이란

공고 내용을 “의미 벡터”라는 숫자로 변환해두면, 검색할 때도 같은 방식으로 변환한 뒤 “의미가 가장 가까운” 공고를 찾을 수 있습니다. 그래서 “GPU 지원”이라고 검색하면, 그 단어가 본문에 없어도 실제로 GPU 관련 지원사업을 찾아냅니다.

In this project

시맨틱 검색용 의미 벡터에는 이미 pgvector의 HNSW 색인을 적용해, 542건 중에서도 빠르게 검색되도록 구성했습니다. 지금은 같은 원리를 확장해, ① 마감일(application_deadline) 컬럼에 색인을 추가해 “접수중” 공고만 즉시 걸러내고, ② 담당 부처(dept) 컬럼에 색인을 추가해 부처별 조회 속도를 높이고, ③ 공고 상태(application_status)에 복합 색인을 적용해 페이지네이션 속도를 개선하는 작업을 진행하고 있습니다. 데이터가 수천, 수만 건으로 늘어나도 검색·조회 속도가 크게 느려지지 않는 구조를 만드는 것이 목표입니다.
